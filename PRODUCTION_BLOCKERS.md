# DINELY — PRODUCTION BLOCKERS (PRODUCTION_BLOCKERS.md)
**Document Status:** Complete Forensic Inventory of Live Launch Blockers  
**Target Delivery:** Multi-Tenant Restaurant SaaS Platform (`dinely.food`)

---

## 1. Top P0 / P1 Production Blockers

### Blocker 1 (P0): DNS Subdomain Black Hole
- **The Problem:** The core product model stipulates that every restaurant is provisioned a tenant domain: `https://<public-slug>.dinely.food`. QR codes, customer menus, kitchen terminals, waiter terminals, and bar terminals are designed to run under this subdomain.
- **The Reality:** Public DNS for `dinely.food` is hosted on GoDaddy (`ns05.domaincontrol.com` / `ns06.domaincontrol.com`). There is NO wildcard record (`*.dinely.food`). Any attempt to open `https://the-dunk.dinely.food` results in an immediate browser error: `DNS_PROBE_FINISHED_NXDOMAIN`.
- **Cloudflare Disconnect:** The repository includes a Cloudflare Worker in `cloudflare/dinely-tenant-router/`, but `dinely.food` nameservers were never switched to Cloudflare. The Worker is completely dead code in production.
- **Consequence:** 100% of QR codes generated by Dinely fail when scanned by real mobile phones.

### Blocker 2 (P0): Dual Parallel Database Engines (Client Mock vs Backend PostgreSQL)
- **The Problem:** [`frontend/src/packages/api/client.ts`](file:///c:/dineflow%20v3/v3/frontend/src/packages/api/client.ts) contains 5,916 lines of code implementing an in-memory and `localStorage` database (`dinely_production_db_v3`).
- **The Reality:** When an owner creates a restaurant or updates a menu, `client.ts` attempts to `fetch()` the backend. When the backend request fails or takes more than 15-20 seconds (Render cold start), the frontend catches the error and saves the entity only in the user's browser `localStorage`.
- **Consequence:** The owner sees their restaurant on their screen and assumes it was created. But Platform Admin and other terminals query the PostgreSQL database on Render, where the record does not exist.

### Blocker 3 (P0): Free-Tier Render 50-Second Cold Starts & Idle Timeouts
- **The Problem:** The production backend is hosted on Render (`dineflow-v3.onrender.com`).
- **The Reality:** Free/low-tier Render instances spin down after 15 minutes of inactivity. When a new customer or owner accesses the app, the first API request takes 45 to 60 seconds to respond.
- **Consequence:** Frontend network timeouts trigger, causing `client.ts` to fall back to `localStorage` mock data, completely desynchronizing the client from PostgreSQL.

### Blocker 4 (P1): Header-Based Tenant Authentication Bypass
- **The Problem:** In [`backend/dineflow-backend/app/core/security/tenant_auth.py:106-115`](file:///c:/dineflow%20v3/v3/backend/dineflow-backend/app/core/security/tenant_auth.py#L106-L115), any HTTP request containing `X-Staff-Role` and `X-Staff-Restaurant-Id` is accepted as an authenticated staff caller without JWT verification.
- **Consequence:** Complete multi-tenant isolation failure at the API layer. Anyone can forge headers to view, cancel, or modify orders and tables of any restaurant on the platform.

### Blocker 5 (P1): Cross-Tenant Storage Bleeding in Terminals
- **The Problem:** When terminals (Kitchen, Waiter, Customer) are opened at apex paths (e.g. `dinely.food/kitchen` or `dinely.food/customer`), they fall back to `localStorage.getItem('dinely_active_restaurant_id')`.
- **Consequence:** On any device where an owner or tester administered Restaurant A, opening the Customer or Kitchen app immediately binds to Restaurant A instead of the intended tenant.

## 2. Discrepancy: Target Product Vision vs Current Implementation

| System Capability | Target Product Vision (Shopify-Style Multi-Tenant OS) | Current Implementation Reality |
| :--- | :--- | :--- |
| **Tenant Digital Identity** | Independent subdomain (`https://<slug>.dinely.food`) with dynamic routing | DNS non-existent; apex SPA with path-based fallbacks and local storage |
| **Data Authority** | PostgreSQL is the single authoritative source of truth; client is a thin consumer | Client maintains a 5,900-line parallel database that hides backend failures |
| **Restaurant Creation** | Transactional server issuance of ID, unique slug, and lifecycle state | Client creates synthetic `rest-${Date.now()}` and caches it locally |
| **Admin Queue** | Admin monitors live PostgreSQL table populated via atomic onboarding | Admin queue queries Render, misses client-cached restaurants, or falls back to mock |
| **QR System** | Dynamic table QR codes resolve reliably on any mobile network | QR codes encode broken subdomains that fail with DNS lookup errors |
| **Terminal Isolation** | Cryptographically bound staff sessions restricted to specific tenant ID | Unauthenticated header bypass allows arbitrary cross-tenant access |
| **Realtime Engine** | Persistent, reconnecting WebSocket stream with state reconciliation | Dropped after 55s idle on Render; no backfill of missed events |

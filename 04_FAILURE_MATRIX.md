**Document Status:** Complete Forensic Defect & Vulnerability Matrix

**Risk Levels:** P0 (Blocker / Data Loss / Down) | P1 (Critical Degradation) | P2 (Major Usability / Logic Issue) | P3 (Minor Inconvenience)

## 1. Comprehensive System Failure Matrix

| # | Feature / Area | Current Behavior | Expected Behavior | Root Cause | Impact | Priority | Dependencies | Recommended Fix |
|---|---|---|---|---|---|---|---|---|
| **1** | **Backend Service Availability** | `dineflow-v3.onrender.com/healthz` hangs indefinitely (>130s) or times out with 502 Bad Gateway. | Backend responds to health check within 100ms with `{"status": "ok"}`. | Render free-tier instance spinning down; startup lockup during synchronous database pooling or Alembic inspection in `main.py`. | Entire live platform unusable; workspaces and subdomains lock up in infinite spinners. | **P0** | Render Web Service / Neon DB | Upgrade backend to paid always-on tier or configure async warmup; fix startup query lockups; set connection pool timeouts. |
| **2** | **Frontend API Timeout & Resilience** | Client `fetch()` requests in `api/client.ts` have no timeout; promises never resolve or reject when backend hangs. | Frontend displays clean error banner / retry button after 8-10 seconds of no backend response. | Missing `AbortController` timeout on API client fetch wrapper. | Users trapped on white screen with perpetual spinning loader (`"Loading workspaces..."`). | **P0** | `frontend/src/packages/api/client.ts` | Wrap all `fetch` calls in an `AbortSignal.timeout(10000)` with user-friendly error fallbacks. |
| **3** | **Owner Workspace Restoration** | Visiting `dinely.food/workspace` spins infinitely or fails to show newly created restaurants. | Displays card grid of all owned restaurants with status badges (`LIVE`, `PENDING_APPROVAL`, `DRAFT`). | API call `GET /restaurants/owner/my` hangs on dead backend; also client falls back to broken LocalStorage cache keys. | Restaurant owners cannot access their dashboard, setup wizard, or operational links. | **P0** | API Client, Backend Auth Router | Fix backend availability; implement resilient client cache with TTL and clear stale session recovery. |
| **4** | **Subdomain Wildcard Routing** | Navigating to `https://the-dunk.dinely.food` hangs or fails DNS resolution if GoDaddy nameservers are active without CF proxying. | Every `<slug>.dinely.food` subroute proxies seamlessly to single frontend SPA and passes tenant context. | DNS zone delegation mismatch between GoDaddy registrar and Cloudflare Worker wildcard route. | Tenants cannot access their branded domains or share QR links with diners. | **P0** | Cloudflare Workers, Registrar DNS | Ensure authoritative NS points to Cloudflare with `*.dinely.food` proxied (orange cloud) to the tenant router worker. |
| **5** | **Tenant Resolution on Subdomains** | Subdomains call `GET /public/resolve?subdomain=the-dunk` which hangs on dead backend. | Instant tenant resolution (<150ms) extracting `slug` and binding `restaurant_id`. | Subdomain resolution route is blocked by downstream backend unresponsive state; no edge caching. | Customer menu never loads; terminal staff cannot log in. | **P0** | Backend Restaurant Router, Cloudflare | Cache verified restaurant slug-to-ID mappings at Cloudflare Edge KV or in memory; add client timeout. |
| **6** | **Imperative Schema Migrations** | App executes raw SQL `ALTER TABLE ADD COLUMN IF NOT EXISTS` inside `main.py` startup function. | Schema managed strictly through declarative Alembic migration scripts (`alembic upgrade head`). | Alembic migration files were abandoned in favour of manual `execute(text(...))` in `_background_startup_init()`. | High risk of race conditions, migration drift, table lockups on restart, and un-reproducible local/prod environments. | **P0** | Database Alembic Config | Generate clean declarative Alembic migration covering all active columns; delete imperative startup SQL alterations. |
| **7** | **Destructive Auto-Purge at Startup** | `main.py` runs `run_clean_production_applications()` on every application boot, archiving records matching hardcoded names like `the-dunk`. | Production database NEVER executes destructive or archiving logic automatically on server restart. | Legacy cleanup script hardcoded into startup lifecycle. | Risk of real production restaurants or test accounts named "The Dunk" being arbitrarily archived on server restart! | **P0** | `main.py`, `cleanup.py` | Permanently remove `run_clean_production_applications()` from startup lifecycle; make cleanup a manual, authenticated admin CLI script. |
| **8** | **Missing Backend Inventory Endpoints** | `app/modules/inventory/` is an empty stub with no registered router in `main.py`. | Fully functional inventory API (`GET /inventory`, `POST /inventory/deduct`, `PATCH /inventory/stock`). | Frontend was built with mock local storage cache while backend module was left un-implemented. | Inventory terminal works only in browser memory; multi-device sync is completely broken. | **P1** | Backend Modules, Frontend Inventory Terminal | Implement full `inventory` router and service layer; persist items and stock transactions in PostgreSQL. |
| **9** | **Missing Backend Waiter Floor Endpoints** | Waiter terminal floor plan and staff assignment calls rely on mock local storage methods in `client.ts`. | Centralized floor plan API tracking table occupancy, waiter assignments, and live alerts in PostgreSQL. | `app/modules/waiters/` was left as an empty directory with no router registered in `main.py`. | Different waiter devices do not see real-time updates when another waiter accepts a table request. | **P1** | Backend Customer Requests & Waiter Router | Consolidate floor management and table assistance requests in `app/modules/customer_requests/router.py`. |
| **10** | **Operational Terminal Staff Authentication** | Terminals accept `X-Staff-Role` and `X-Staff-Restaurant-Id` headers without cryptographic token verification. | Terminal PIN code verification (`POST /auth/terminal-login`) returning scoped short-lived staff JWT. | Trust-based terminal role header architecture designed for local development. | Anyone with developer tools can spoof `X-Staff-Role: WAITER` or `KITCHEN` to manipulate orders. | **P1** | Backend Auth Router & Middleware | Implement 4-digit staff PIN authentication generating cryptographically signed role-scoped JWT tokens. |
| **11** | **Admin Approval Realtime Notification** | When an owner submits a restaurant, Platform Admin UI does not always update in real time without manual reload. | Admin dashboard receives WebSocket event `"restaurant_submitted"` and updates pending badge immediately. | Admin UI WebSocket connection lacks heartbeat ping-pong; disconnects silently on background tab. | Platform Admin misses incoming restaurant submissions, delaying restaurant onboarding. | **P2** | Realtime Bus, WebSocket Manager | Add WebSocket heartbeat ping/pong (every 30s) and automatic query re-fetching on reconnect. |
| **12** | **Dynamic QR Code Domain Generation** | Some legacy frontend views use `window.location.origin` or fallback domains when rendering QR placards. | All QR codes generate strictly formatted URL: `https://<slug>.dinely.food/customer?table=XX`. | Scattered QR generation logic between `SetupWizard.tsx`, `RestaurantDashboard.tsx`, and `client.ts`. | If owner generates QR from `localhost` or `dinely.food/workspace`, QR placard encodes incorrect domain! | **P0** | Frontend QR Generators | Centralize all QR encoding into a single authoritative utility `getRestaurantCustomerUrl(slug, table)`. |
| **13** | **Table Number Format Inconsistency** | Orders placed for table `"01"` fail to match bills or floor tables stored as `"1"` or `"Table 1"`. | Flexible table normalization engine matches `"1"`, `"01"`, and `"Table 1"` consistently across all queries. | Different apps format table strings differently before sending to database. | Customer orders fail to link to active table sessions; bills generated for table appear empty. | **P1** | Orders Router, Billing Router, `tableUtils.ts` | Normalize all table numbers to clean uppercase alphanumeric strings (`formatStandardTableNumber`) on DB write and read. |
| **14** | **Unbounded Database Queries in Admin/Orders** | Admin restaurant list and orders endpoint execute unbounded `SELECT *` queries without pagination. | Queries enforce `limit = 50`, `offset`, and cursor-based pagination with indexed date filters. | Simple prototype queries never updated for production data volume. | Database query time will degrade exponentially as restaurants and orders scale past 1,000 records. | **P2** | SQLAlchemy Service Queries | Implement pagination schemas and indices on `created_at`, `status`, and `restaurant_id`. |
| **15** | **Cross-Tenant Event Broadcasting Risk** | WebSocket manager does not strictly validate whether a socket connection is authorized for the target `restaurant_id`. | WebSocket handshake validates caller's membership or table session before joining room `restaurant:{id}`. | Prototype `ConnectionManager` allows any client connecting to `/ws/{id}` to listen to room events. | Critical security risk: rogue client could listen to orders and customer requests of competing restaurants. | **P0** | `app/modules/websocket/router.py` | Add JWT token verification to WebSocket query parameter; enforce restaurant membership check on connection. |
| **16** | **Monolithic Frontend API Client** | `frontend/src/packages/api/client.ts` is 5,914 lines of mixed real API calls, mock data fallbacks, and local storage overrides. | Modular, clean typed API client where each domain (`orders`, `menu`, `auth`, `billing`) has its own service file. | Iterative feature additions were continually appended to a single prototype file. | Extreme code fragility; hard to debug; accidental fallbacks to mock data mask production API bugs. | **P2** | Frontend API Package | Split `client.ts` into domain services (`authService.ts`, `orderService.ts`, `menuService.ts`, `tenantService.ts`). |
